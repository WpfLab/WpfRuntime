# WpfDemo In-Repo WPF Implementation

## Goal / bounds

`Demo/WpfDemo` is the development and runtime-probe host for in-repo WPF. After WPF implementations are built, it is responsible for:

- Letting C# and XAML use automatically generated reference assemblies from implementation projects.
- Deploying in-repo WPF managed implementations, theme assemblies, and x64 native assets as app-local files.
- Using `.deps.json` and `.runtimeconfig.json` so the app runs without the `Microsoft.WindowsDesktop.App.WPF` shared framework.
- Verifying load sources of key managed assemblies and native modules in the UI or `--verify-repo-wpf` mode.

The current consumption pipeline supports only `Debug|x64`. `x86`, `arm64`, and Publish are not implemented. Solution `Any CPU` only maps to the WpfDemo project's `x64` and does not mean WpfDemo has an AnyCPU runtime closure.

This document describes only WpfDemo's current implementation contract. Whole-repository status is owned by [00-overview.md](00-overview.md). Later work is owned by [01-phase-plan.md](01-phase-plan.md).

## Project and shared files

WpfDemo project-side files:

- `Demo/WpfDemo/WpfDemo.csproj`: declares the WPF app, x64 platform, and build dependencies, and imports the in-repo `Microsoft.WinFX.targets` after SDK targets.
- `Demo/WpfDemo/Directory.Build.props`: inherits repository-root props first, then imports `eng/WpfDemo/RepoWpfConsumer.props`.
- `Demo/WpfDemo/Directory.Build.targets`: inherits repository-root targets first, then imports `eng/WpfDemo/RepoWpfConsumer.targets`.
- `Demo/WpfDemo/Diagnostics/WpfRuntimeProbe.cs`: asserts app-local sources for managed assemblies, C++/CLI assemblies, and native modules.
- `Demo/WpfDemo/App.xaml.cs` and `MainWindow.xaml.cs`: wire automatic probes, verification reports, and exit codes.

Shared build files:

- `eng/WpfDemo/RepoWpfConsumer.props`: imports shared version and asset inventories, sets repo-WPF consumption switches, and declares runtime packages.
- `eng/WpfDemo/RepoWpfConsumer.targets`: replaces compile references, collects runtime assets per project, registers deps, copies resources and native files, and validates output.
- `eng/WpfRuntimeDependencies.props`: target framework, WindowsDesktop runtime version, NuGet packages, compile assemblies, runtime assemblies, theme projects, and native-file inventory shared by Builder and WpfDemo.
- Root `Directory.Build.targets`: imports in-repo markup-compile targets for `InternalMarkupCompilation=true` projects and handles shared generation logic for `NoInternalTypeHelper=true`.
- `Microsoft.Dotnet.Wpf.slnx`: declares WpfDemo and its solution platform mapping.

The shared version and asset inventories are already implemented. Do not create same-named version constants or copied inventories inside the WpfDemo project. `eng/WpfRuntimeDependencies.props` imports `eng/Versions.props` as needed. The current WindowsDesktop x64 runtime version is `8.0.6`.

## Build dependency, not runtime reference

WpfDemo uses these settings against `PresentationFramework.csproj` and the seven external theme projects:

- `Targets="Restore;Build"`
- `ReferenceOutputAssembly="false"`

These `ProjectReference`s only establish restore, build, and incremental-build order. They do not inject project outputs into WpfDemo as ordinary compile or runtime references. That avoids putting implementation assemblies, automatic refs, hand-written refs, SDK inbox assemblies, and same-named cycle-breaker assemblies into the XAML or C# reference graph at the same time.

`PresentationFramework` is the top-level build dependency of the managed main chain. Theme assemblies are loaded by the runtime by theme name, so the seven theme projects are added as explicit build dependencies. Runtime assets are collected item-by-item from the shared inventory and do not depend on `ProjectReference` transitive copy behavior.

## Automatic ref references

WpfDemo removes the implicit `Microsoft.WindowsDesktop.App.WPF` FrameworkReference, cleans same-named WPF references resolved by the SDK or projects after `ResolveReferences`, then injects automatic refs generated by implementation projects:

```text
artifacts/obj/<Assembly>/x64/Debug/net8.0/ref/<Assembly>.dll
```

The current compile inventory is:

- `WindowsBase`
- `System.Xaml`
- `System.Windows.Input.Manipulations`
- `UIAutomationTypes`
- `UIAutomationProvider`
- `PresentationCore`
- `PresentationFramework`

Replacement covers `ReferencePath`, `ReferencePathWithRefAssemblies`, and `ReferenceDependencyPaths`. Automatic refs are generated with the implementation project's public API, so WpfDemo does not use hand-written `*-ref.csproj` files as the primary compile contract for new-API experiments.

The in-repo `PresentationBuildTasks/Microsoft.WinFX.targets` is imported after SDK targets, so C# and XAML share the same automatic-ref set. If any ref output is missing, a non-design-time build reports the specific missing path.

## Per-project runtime collection

The current implementation no longer copies the entire `PresentationFramework` output directory as a runtime closure. That approach belonged to an early prototype, treated transitive copies as project primary outputs, and could hide version or source errors.

The current implementation walks `RepoWpfRuntimeAssembly` and collects each assembly's primary DLL from its owning project's output directory:

```text
artifacts/bin/<Assembly>/x64/Debug/net8.0/<Assembly>.dll
```

`DirectWriteForwarder.dll` is located separately using its C++/CLI project output layout. Culture resource assemblies are currently collected with `<ProjectOutput>\*\<Assembly>.resources.dll`, and the copy destination depends on `%(RecursiveDir)`. That pattern does not produce stable `RecursiveDir` metadata from a recursive wildcard, so it has not been proven to preserve culture subdirectories. Same-named satellite assemblies from different cultures may be flattened or overwritten.

The shared runtime inventory includes core WPF, ReachFramework, PresentationUI, Ribbon, WindowsFormsIntegration, UIAutomation, the seven theme assemblies, and `DirectWriteForwarder`. Items with `WpfDemoRequired=true` fail immediately when missing. Other items are included only when the project primary output exists.

`System.Printing` is not in the current WpfDemo runtime inventory. Printing-implementation migration and build status are other repository work items. Do not add `System.Printing.dll` to the current WpfDemo runtime closure from that fact.

## deps / runtimeconfig

Collected implementation assemblies are added to:

- `ReferenceDependencyPaths`, with `IncludeRuntimeDependency=true`.
- `ReferenceCopyLocalPaths`, used to copy into the WpfDemo output directory.

Those two steps write runtime assemblies into `WpfDemo.deps.json` and deploy them to the application directory. Copying DLLs without registering deps cannot form a reliable app-local runtime contract.

Post-build validation includes:

- `WpfDemo.runtimeconfig.json` and `WpfDemo.deps.json` must exist.
- `runtimeconfig` must not contain `Microsoft.WindowsDesktop.App`.
- `deps` must register `WindowsBase.dll`, `PresentationCore.dll`, `PresentationFramework.dll`, and `DirectWriteForwarder.dll`.
- The output directory must contain the key managed assemblies, `ijwhost.dll`, and key native WPF files.

`ReferenceOutputAssembly=false` cuts natural transitive flow of upstream project package dependencies, so WpfDemo explicitly references runtime NuGet packages from the shared `RepoWpfRuntimePackage` inventory. Builder and WpfDemo use the same version source.

## Theme BAML and native / ijwhost deployment

The seven theme projects are:

- `PresentationFramework.Aero`
- `PresentationFramework.Aero2`
- `PresentationFramework.AeroLite`
- `PresentationFramework.Classic`
- `PresentationFramework.Fluent`
- `PresentationFramework.Luna`
- `PresentationFramework.Royale`

They are both explicit build dependencies and per-project runtime-collection entries. Output validation uses PE metadata to read each theme DLL, confirm `<AssemblyName>.g.resources` exists, and confirm the corresponding file name is registered in `WpfDemo.deps.json`. Checking that the DLL exists is not enough to prove theme BAML was generated.

x64 native files come from the shared version of `Microsoft.WindowsDesktop.App.Runtime.win-x64`. The current inventory is:

- `D3DCompiler_47_cor3.dll`
- `PenImc_cor3.dll`
- `PresentationNative_cor3.dll`
- `vcruntime140_cor3.dll`
- `wpfgfx_cor3.dll`

`DirectWriteForwarder.dll` is collected from its project primary output. `ijwhost.dll` is copied from the same C++/CLI build output and uses the official file name in the WpfDemo directory. The build fails if a source file is missing, instead of filling the closure from machine shared-framework files.

`PresentationCore` module initialization currently calls `DWriteLoader.LoadDWrite()`. A `UnloadDWrite()` definition has been found in the code, but a corresponding call has not been confirmed, so DWrite release at process exit cannot be claimed as verified.

## Runtime probe

`WpfRuntimeProbe` is implemented. It verifies:

- Process architecture must be x64.
- Actual locations of `WindowsBase`, `PresentationCore`, and `PresentationFramework` must equal the expected files in the WpfDemo output directory.
- The three core assemblies must target `.NETCoreApp,Version=v8.0` and have assembly version `8.0.0.0`.
- `DirectWriteForwarder.dll` must load as an app-local C++/CLI assembly.
- `PenImc_cor3.dll`, `PresentationNative_cor3.dll`, and `wpfgfx_cor3.dll` must load from the application directory and be found in the current process modules.

Ordinary startup runs the probe after window content is presented and the Dispatcher reaches `ApplicationIdle`, then displays the result. With `--verify-repo-wpf`, the app writes `WpfDemo.repo-wpf-validation.txt`, returns 0 on success, and returns a non-zero exit code on verification failure.

The probe verifies architecture, version, and actual load location of the checked modules. It does not replace a full solution build, all WPF functionality, or Visual Studio debug-path verification.

## Platform mapping

The WpfDemo project declares `Platforms=x64` and `PlatformTarget=x64`. Consumer targets also reject non-`Debug` configurations and non-`x64` platforms.

Current `Microsoft.Dotnet.Wpf.slnx` mapping:

- Solution `Any CPU` -> WpfDemo project `x64`
- Solution `x64` -> WpfDemo project `x64`

WpfDemo has no `x86` or `arm64` mapping. A successful solution `Any CPU` mapping only means WpfDemo selected the x64 project configuration. A full `Debug|Any CPU` build still needs separate verification under the bounds in [00-overview.md](00-overview.md).

- WpfDemo x64 consumption, shared version and asset inventories, automatic refs, per-project runtime collection, deps/runtimeconfig validation, theme BAML validation, native/ijwhost deployment, and the runtime probe are implemented. - Current full-solution build status is maintained only in [00-overview.md](00-overview.md).
- The projects and probe implementation needed for Visual Studio F5 already exist, but F5 has not been re-verified.
- `x86`, `arm64`, and Publish are not implemented.
- DWrite exit release has not been verified. Currently only the `UnloadDWrite()` definition is confirmed, not a call.
